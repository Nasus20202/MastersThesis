# Skills development evaluation

## Status

This study evaluates the troubleshooting skill agent for the five Kubernetes development scenarios used by tickets [#15](https://github.com/Nasus20202/MastersThesis/issues/15)–[#18](https://github.com/Nasus20202/MastersThesis/issues/18). Runs 1–7 form the skill revision series. Run 6 remains the selected skill revision because it was the strongest revision that consistently routed domain skills and references. Run 8 is the final three-condition benchmark and completed all 75 attempts.

Run 8 used the Run 6 skill files, a 600-second total agent limit, and an 8 KiB model-visible limit for each Bash result. Full command output remains in the raw attempt evidence.

## Question

Does structured troubleshooting guidance, with routed Kubernetes skills and references, improve repair outcomes and tool use on the five development scenarios?

## Method

The initial run compared `baseline`, `prompt`, and `skill`. Runs 2–7 evaluated successive `skill` revisions. Run 8 compared the three conditions with the selected skill revision and final harness settings. Each condition and scenario used five independent attempts. The five scenarios were `container-crash-loop`, `image-pull-failure`, `missing-rbac-binding`, `service-selector-mismatch`, and `unschedulable-cpu-request`.

The primary measure is the macro-average normalized score: the mean score for each scenario, followed by an unweighted mean across scenarios. Full success requires every deterministic grading criterion to pass. The table also reports failed attempts caused by model-agent, verification, or cleanup errors. The scorer includes those attempts with their recorded score, normally zero; therefore the scores measure end-to-end performance under the configured limits.

The model was Gemma 4 E4B QAT Q4_0, served by the pinned llama.cpp Vulkan image. Attempts allowed 25 turns, 50 tool calls, and 60 seconds per tool call. Runs 1–7 used a 300-second total limit; Run 8 used 600 seconds and capped model-visible Bash output at 8 KiB. Scenario order in the score column is crash, image, RBAC, service, CPU. Skill and reference columns count load tool calls in the archived traces; repeated loads count repeatedly.

Run 2 is not selected despite its higher score because it did not test the intended domain-routing behavior. Run 6 is the strongest revision among runs that consistently loaded the troubleshooting and Kubernetes skills and used focused references. Run 7 added a generic patch rule, but its score and full-success count fell and its failed Bash-call rate increased.

## Conclusions

In the final benchmark, both the prompt and skill conditions scored 0.820 versus 0.700 for the baseline. The skill condition produced 20 full successes, one more than the prompt condition and four more than the baseline. Its largest relative gain was on the RBAC scenario, where it reached a mean score of 1.000; its crash-loop score remained 0.200 and its image-pull score 0.900.

The final data support retaining Run 6 as the skill revision: it produced the highest full-success count while loading domain guidance in every skill attempt. The equal macro score for prompt and skill means the final benchmark does not show a uniform outcome advantage for the skill condition. One skill attempt ended with a model-agent context deadline and remains in the denominator.

## Limitations

The results are descriptive rather than causal. Runs were sequential and unpaired, the skill text changed between runs, and Run 8 also changed the total time limit and model-visible output cap. The final comparison therefore estimates performance under the final harness; it does not isolate the effect of the skill text alone.
