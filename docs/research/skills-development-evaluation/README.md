# Skills development evaluation

## Status

This study evaluates the troubleshooting skill agent for the five Kubernetes development scenarios used by tickets [#15](https://github.com/Nasus20202/MastersThesis/issues/15)–[#18](https://github.com/Nasus20202/MastersThesis/issues/18). Seven runs are complete. Run 6 is the selected skill revision for the next benchmark. The later Run 7 revision did not improve the score. A three-condition run was interrupted at 57 of 75 attempts and is excluded from the comparison.

The next benchmark uses the Run 6 skill files, a 600-second total agent limit, and an 8 KiB model-visible limit for each Bash result. Full command output remains in the raw attempt evidence. These settings have not yet been benchmarked.

## Question

Does structured troubleshooting guidance, with routed Kubernetes skills and references, improve repair outcomes and tool use on the five development scenarios?

## Method

The initial run compared `baseline`, `prompt`, and `skill`. Runs 2–7 evaluated successive `skill` revisions. Each condition and scenario used five independent attempts. The five scenarios were `container-crash-loop`, `image-pull-failure`, `missing-rbac-binding`, `service-selector-mismatch`, and `unschedulable-cpu-request`.

The primary measure is the macro-average normalized score: the mean score for each scenario, followed by an unweighted mean across scenarios. Full success requires every deterministic grading criterion to pass. The table also reports failed attempts caused by model-agent, verification, or cleanup errors. The scorer includes those attempts with their recorded score, normally zero; therefore the scores measure end-to-end performance under the configured limits.

The model was Gemma 4 E4B QAT Q4_0, served by the pinned llama.cpp Vulkan image. Attempts allowed 25 turns, 50 tool calls, and 60 seconds per tool call. Runs 1–7 used a 300-second total limit; the next benchmark uses 600 seconds. Scenario order in the score column is crash, image, RBAC, service, CPU. Skill and reference columns count load tool calls in the archived traces; repeated loads count repeatedly.

Run 2 is not selected despite its higher score because it did not test the intended domain-routing behavior. Run 6 is the strongest revision among runs that consistently loaded the troubleshooting and Kubernetes skills and used focused references. Run 7 added a generic patch rule, but its score and full-success count fell and its failed Bash-call rate increased.

The results are descriptive rather than causal. Runs were sequential and unpaired, the skill text changed between runs, and several attempts ended through runtime or verification errors. The context-overflow attempts identify a harness limitation rather than a successful or unsuccessful repair; the next run addresses that limitation by bounding model-visible command output.
