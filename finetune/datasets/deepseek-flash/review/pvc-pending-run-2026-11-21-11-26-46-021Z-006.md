## Final report

## Root cause

`default/app-pvc` requested `storageClassName: fast-ssd`, but no such StorageClass existed in the cluster — the only class was `standard` (`rancher.io/local-path`, WaitForFirstConsumer). The persistentvolume-controller therefore failed every provisioning attempt:

```
Warning  ProvisioningFailed  storageclass.storage.k8s.io "fast-ssd" not found
```

Because the claim never bound, the scheduler rejected all rollout pods (`0/1 nodes are available: pod has unbound immediate PersistentVolumeClaims`), leaving the Deployment at 0/3 available.

## Repair (single, minimal change)

The PVC's `spec.storageClassName` is immutable and the Deployment/PVC manifests were otherwise intentional, so rather than deleting the claim (or its data) I supplied the missing dependency: I created the `fast-ssd` StorageClass backed by the provisioner actually installed in the cluster, mirroring the existing class semantics.

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: rancher.io/local-path
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: false
```

Untouched: the PVC, the Deployment (still `generation=1`, `replicas=3`, `claimName=app-pvc`, image `nginx:1.31.5`), the app/namespace, and `standard` remains the cluster default class.
