# image-pull-failure · deepseek-flash · run-2026-11-21-11-26-46-021Z · attempt 3

## Task

An application in the Kubernetes cluster is unhealthy. Restore it to a healthy state.

Documented in:

- content/en/docs/concepts/containers/images.md: Updating images > ImagePullBackOff

## Final report

The application is restored.

## What was wrong

The `app` Deployment in namespace `default` had a typo in the container image name: `ngnix:1.31.5` instead of `nginx:1.31.5`. The rolling update created a new ReplicaSet (`app-5866bbf94f`) whose pod `app-5866bbf94f-pf9zb` went to `ImagePullBackOff`, with the kubelet reporting:

```
Failed to pull image "ngnix:1.31.5": ... docker.io/library/ngnix:1.31.5: not found
```

That left the Deployment stuck progressing: `spec.replicas=3` but `updatedReplicas=1`, `unavailableReplicas=1`, with only the old ReplicaSet's 3 pods serving traffic.

## Change made

A single, targeted strategic-merge patch to the owning Deployment, changing only the container image (replicas, strategy, ports, labels, and everything else left intact):

```
kubectl patch deploy app -n default --type=strategic \
  -p '{"spec":{"template":{"spec":{"containers":[{"name":"app","image":"nginx:1.31.5"}]}}}}'
```

## Verified outcome

- Rollout completed: `deployment "app" successfully rolled out`; conditions now `Available=True (MinimumReplicasAvailable)` and `Progressing=True (NewReplicaSetAvailable)`.
- Replica counts match the requested count exactly: `spec.replicas=3`, `updatedReplicas=3`, `readyReplicas=3`, `availableReplicas=3`, `unavailableReplicas` empty; `kubectl get deploy` shows `3/3 READY, 3 UP-TO-DATE, 3 AVAILABLE`.
- Running image is the intended one on all pods: `nginx:1.31.5`, resolved `imageID=docker.io/library/nginx@sha256:05b8cb60c354a44ab824ea6e7dc69b46d50762cdbe728a347a5b656e6fb3d7c4`.
- Actual request check through each pod (not just object health): `http_code=200` for all three pod IPs (10.244.0.4, 10.244.0.6, 10.244.0.7) on port 80.
- The broken pod `app-5866bbf94f-pf9zb` no longer exists (deleted by the rollout); the remaining `Failed`/`BackOff` events reference only that deleted pod, and no new warning events are being generated. All 3 pods are `Running`.
