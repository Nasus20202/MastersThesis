# pvc-pending · deepseek-flash · run-2026-11-21-11-26-46-021Z · attempt 5

## Task

An application rollout is not completing because its PersistentVolumeClaim is stuck Pending. Restore the application to a healthy state with the claim bound.

Documented in:

- content/en/docs/concepts/storage/persistent-volumes.md: Lifecycle of a volume and claim > Binding, PersistentVolumeClaims > Class

## Write commands

1. `kubectl patch pvc app-pvc -n default --type merge -p '{"spec":{"storageClassName":"standard"}}' --dry-run=server 2>`
2. `kubectl apply -f - 2>`

## Final report

The application is healthy and the claim is bound.

## Root cause

`app-pvc` (namespace `default`) requested `storageClassName: fast-ssd`, but no such StorageClass existed in the cluster — only the default `standard` class. The provisioner therefore failed:

```
Warning  ProvisioningFailed  storageclass.storage.k8s.io "fast-ssd" not found
```

As a result the PVC stayed `Pending`, all 3 pods were unschedulable (`pod has unbound immediate PersistentVolumeClaims`), and the Deployment reported `MinimumReplicasUnavailable`.

## Change made

Retargeting the claim was not possible — the API server rejected it, confirming the constraint:

```
spec: Forbidden: spec is immutable after creation except resources.requests and volumeAttributesClassName for bound claims
```

So I made the single minimal change of supplying the missing storage class, using the provisioner already installed in the cluster (`rancher.io/local-path`, same as `standard`) with `WaitForFirstConsumer` binding so the volume is created on the node where the pod lands — leaving the PVC, Deployment, and the default class untouched:

```yaml
kind: StorageClass
metadata: { name: fast-ssd }
provisioner: rancher.io/local-path
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
```
