# pvc-pending · deepseek-flash · run-2026-11-21-11-26-46-021Z · attempt 7

## Task

An application rollout is not completing because its PersistentVolumeClaim is stuck Pending. Restore the application to a healthy state with the claim bound.

Documented in:

- content/en/docs/concepts/storage/persistent-volumes.md: Lifecycle of a volume and claim > Binding, PersistentVolumeClaims > Class

## Write commands

1. `kubectl patch pvc app-pvc -p '{"spec":{"storageClassName":"standard"}}' --dry-run=server`
2. `kubectl apply -f /tmp/fast-ssd.yaml`

## Final report

The rollout completed and the claim is bound.

## Root cause

`app-pvc` requested `storageClassName: fast-ssd`, but no such StorageClass existed in the cluster — the only class was `standard` (`rancher.io/local-path`, default). The PVC controller reported:

```
Warning  ProvisioningFailed  storageclass.storage.k8s.io "fast-ssd" not found
```

Since the class used `WaitForFirstConsumer` semantics, the three `app` pods could never be placed either:

```
Warning  FailedScheduling  0/1 nodes are available: pod has unbound immediate PersistentVolumeClaims
```

The PVC's `spec.storageClassName` is immutable (`spec: Forbidden: spec is immutable after creation...`), so the PVC itself could not be edited in place.

## Change made

Created the missing cluster-scoped StorageClass that the claim already referenced, backed by the cluster's only working provisioner (matching the existing `standard` class's `WaitForFirstConsumer` binding so the volume is placed on the node the pod lands on):

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: rancher.io/local-path
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
```

Nothing else was modified — the PVC, its 1Gi/RWO request, the Deployment, its replica count, and the `nginx:1.31.5` image were all left as declared. No object needed deleting or recreating.
