## Final report

The application is stable and Ready. Summary of what I found and did:

**Diagnosis (evidence)**

- `kubectl get pods -A` showed both `default/app` pods in `OOMKilled` with 5 restarts each, `READY 0/1`.
- `kubectl describe pod` showed container `app` (image `nginx:1.31.5`) with `Limits: memory: 4Mi`, exit code 137, `Reason: OOMKilled` on every attempt — including at container init.
- Events confirmed it: `container init was OOM-killed (memory limit too low?)`.
- Comparing ReplicaSets: rev. 1 `app-6b5786fd` had `limits.memory: 64Mi`; rev. 2 `app-774f56f755` had `4Mi` — the only difference in the pod template. No `LimitRange` or `ResourceQuota` exists, and the node has ~32Gi allocatable, so nothing forced the tiny limit; it was a bad value in the Deployment.

**Fix (smallest justified change)**
Restored the known-good value on the owning persistent resource, the Deployment, leaving all other settings (image, ports, probes, strategy, replicas) untouched:

```
kubectl patch deployment app -n default --type=json \
  -p='[{"op":"replace","path":"/spec/template/spec/containers/0/resources/limits/memory","value":"64Mi"}]'
```

**Verification (fresh observations)**

- `limits=64Mi` on the live Deployment; new ReplicaSet `app-6b5786fd` rolled out successfully (`deployment "app" successfully rolled out`).
- Controller counts match the request exactly: **2 requested / 2 replicas / 2 updated / 2 ready / 2 available**.
- Both pods `READY true`, `RESTARTS 0`, `LASTTERM <none>` after ~2 minutes of runtime — no further OOM kills.
- Functional check through the container's serving port: `curl http://127.0.0.1:80/` from inside each pod returned **HTTP 200**.
- Event log's newest entry is the container `Started` at `12:00:07Z`; no `OOMKilled`, `Failed`, or `BackOff` events since the patch. (The single `Unhealthy` readiness probe lines at 12:00:07 were the expected sub-second startup window before nginx bound port 80; readiness has been `True` continuously since.)
