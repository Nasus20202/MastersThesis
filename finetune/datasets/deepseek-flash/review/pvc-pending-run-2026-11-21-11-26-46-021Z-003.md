# pvc-pending · deepseek-flash · run-2026-11-21-11-26-46-021Z · attempt 3

## Task

An application rollout is not completing because its PersistentVolumeClaim is stuck Pending. Restore the application to a healthy state with the claim bound.

Documented in:

- content/en/docs/concepts/storage/persistent-volumes.md: Lifecycle of a volume and claim > Binding, PersistentVolumeClaims > Class

## Write commands

1. `kubectl apply -f -`

## Final report

## Root cause

The PVC `default/app-pvc` requests `storageClassName: fast-ssd`, but that StorageClass did not exist in the cluster — only `standard` did. Evidence:

- PVC status: `Pending`, unbound, no volume.
- PVC event: `Warning ProvisioningFailed ... storageclass.storage.k8s.io "fast-ssd" not found` (repeating every ~15s).
- Controller-manager log: `Error finding provisioning plugin for claim err="storageclass.storage.k8s.io \"fast-ssd\" not found" PVC="default/app-pvc"`.
- Pod events: `0/1 nodes are available: pod has unbound immediate PersistentVolumeClaims`.
- The local-path provisioner was healthy (1/1) and had previously provisioned this claim successfully, so the missing StorageClass — not the provisioner — was the fault.

## Change made

`storageClassName` on a PVC is immutable, and the claim is the persistent resource owning the state, so instead of deleting the PVC (a delete-based "fix" that would also discard the claim's identity) I restored the missing dependency: created the `fast-ssd` StorageClass backed by the cluster's existing provisioner, with settings matching the working `standard` class and no other cluster settings altered (`standard` remains the default class):

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata: { name: fast-ssd }
provisioner: rancher.io/local-path
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
```

- Deployment: `kubectl rollout status` → "successfully rolled out"; replicas requested/updated/ready/available = **3/3, 3, 3, 3**; conditions `Available=True (MinimumReplicasAvailable)`, `Progressing=True (NewReplicaSetAvailable)`.
- Pods: 3/3 `Running`, `READY true`, `RESTARTS 0`.
- Storage actually works through the claim: wrote and read `/data` in all three pods, and a file written by `app-74bbc8b6cc-69f7p` was readable from `app-74bbc8b6cc-8wdww` (`shared-check`), with `/data` mounted from the provisioned volume.

Only the missing StorageClass was added; the deployment, PVC, and other StorageClasses were left untouched.
