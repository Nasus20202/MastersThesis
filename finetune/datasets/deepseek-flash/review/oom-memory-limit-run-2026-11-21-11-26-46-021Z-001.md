# oom-memory-limit · deepseek-flash · run-2026-11-21-11-26-46-021Z · attempt 1

## Task

A Kubernetes application is restarting repeatedly and never stays healthy. Restore it to a stable, Ready state.

Documented in:

- content/en/docs/tasks/configure-pod-container/assign-memory-resource.md: Specify a memory request and a memory limit, Exceed a Container's memory limit

## Write commands

1. `kubectl auth can-i patch deployments -n default 2>`
2. `kubectl patch deployment app -n default --type=json -p='[{"op":"replace","path":"/spec/template/spec/containers/0/resources/limits/memory","value":"64Mi"}]' 2>`

## Final report

The application is stable and serving traffic.

## Root cause

The `app` Deployment in the `default` namespace was configured with a **`memory: 4Mi` limit** — far below what the nginx container's init process needs. The kubelet events showed the container never even fully started:

```
Warning  Failed  Error: failed to create containerd task: ... container init was
OOM-killed (memory limit too low?)
```

This produced `StartError` (exit code 128) → `CrashLoopBackOff`, 6+ restarts per pod, and readiness probes failing with `connection refused`.

Evidence that this was the regression: the previous ReplicaSet `app-6b5786fd` (revision 1) used `{"limits":{"memory":"64Mi"}}`, while revision 2 dropped it to `4Mi`. No LimitRange or ResourceQuota existed in the namespace, so nothing mandated the low value — it was purely a bad setting.

## Fix applied

One minimal change — restored the previously-working memory limit:

```
kubectl patch deployment app -n default --type=json \
  -p='[{"op":"replace","path":"/spec/template/spec/containers/0/resources/limits/memory","value":"64Mi"}]'
```

Everything else (image `nginx:1.31.5`, replicas `2`, readiness probe, Recreate strategy) was left untouched. The node had 32Gi allocatable with only 348Mi in limits, so 64Mi was comfortable.
