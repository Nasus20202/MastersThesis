# pvc-pending · deepseek-flash · run-2026-11-21-11-26-46-021Z · attempt 1

## Task

An application rollout is not completing because its PersistentVolumeClaim is stuck Pending. Restore the application to a healthy state with the claim bound.

Documented in:

- content/en/docs/concepts/storage/persistent-volumes.md: Lifecycle of a volume and claim > Binding, PersistentVolumeClaims > Class

## Write commands

1. `kubectl patch pvc app-pvc -n default --type=merge -p '{"spec":{"storageClassName":"standard"}}' 2>`
2. `kubectl delete pvc app-pvc -n default --timeout=20s 2>`
3. `write_file {"content": "apiVersion: v1\nkind: PersistentVolumeClaim\nmetadata:\n name: app-pvc\n namespace: default\n labels:\n app: app\nspec:\n accessModes:\n - ReadWriteOnce\n resources:\n requests:\n storage: 1Gi\n storageClassName: standard\n volumeMode: Filesystem\n", "path": "/tmp/app-pvc.yaml"}`
4. `kubectl create -f /tmp/app-pvc.yaml 2>`

## Final report

The application is healthy and the claim is bound.

## Root cause

The PVC `default/app-pvc` requested `storageClassName: fast-ssd`, but no such StorageClass exists in this cluster — only `standard` (provisioner `rancher.io/local-path`, default class `WaitForFirstConsumer`). The persistent-volume controller logged repeatedly:

```
Warning  ProvisioningFailed  storageclass.storage.k8s.io "fast-ssd" not found
```

Because the volume-binding mode is `WaitForFirstConsumer`, the 3 `app` pods could not be scheduled until the claim bound (their only volume source was `claimName: app-pvc`), so the Deployment reported `MinimumReplicasUnavailable` with `unavailableReplicas: 3`.

## Fix applied

`spec.storageClassName` is immutable on an existing PVC (the API server rejected an in-place patch: _"spec is immutable after creation except resources.requests and volumeAttributesClassName"_). The claim was unbound and empty, so I recreated it against the class the provisioner actually serves:

- Deleted `app-pvc` (unbound, no PV, no data lost).
- Recreated `app-pvc` with the identical name, namespace, labels (`app: app`), access mode (`ReadWriteOnce`), and size (`1Gi`), changing only `storageClassName: fast-ssd` → `standard`.

No other configuration was touched — the Deployment, its image, replicas, and the StorageClasses themselves are unchanged.
