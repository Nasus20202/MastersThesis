# oom-memory-limit · deepseek-flash · run-2026-11-21-11-26-46-021Z · attempt 3

## Task

A Kubernetes application is restarting repeatedly and never stays healthy. Restore it to a stable, Ready state.

Documented in:

- content/en/docs/tasks/configure-pod-container/assign-memory-resource.md: Specify a memory request and a memory limit, Exceed a Container's memory limit

## Write commands

1. `kubectl -n default patch deployment app --type=strategic -p '{"spec":{"template":{"spec":{"containers":[{"name":"app","resources":{"requests":{"memory":"64Mi"},"limits":{"memory":"128Mi"}}}]}}}}' 2>`

## Final report

The application is restored to a stable, Ready state.

## Root cause

The `app` Deployment in namespace `default` (2 replicas of `nginx:1.31.5`) had a container memory limit of only **`4Mi`**, far below what the nginx process needs even to initialize. Evidence from the failing pods:

- Deployment template: `resources.limits.memory: 4Mi` (no requests set, so requests defaulted to `4Mi`)
- Pod container `Last State: Terminated, Reason: OOMKilled, Exit Code: 137`, restart count 5
- Event: `failed to create containerd task: ... container init was OOM-killed (memory limit too low?)` — the container was killed before it could even start
- `Deployment does not have minimum availability`; 0/2 ready, `unavailableReplicas: 2`

I confirmed there was no LimitRange or ResourceQuota that capped memory, and the node had ~32 GiB allocatable with only 298Mi requested — so the limit itself was the defect, not cluster capacity.

## Change made

Patched only the memory resources on the `app` Deployment, leaving image, ports, probes, strategy (`Recreate`), replica count, labels, and namespace untouched:

```
limits.memory:   4Mi -> 128Mi
requests.memory: 4Mi -> 64Mi
```

QoS class remains `Burstable`, as before. I deliberately did not delete pods or touch the readiness probe — those would not have fixed the recurring OOM kills.

## Verified outcome (fresh observations)

- **Rollout**: `deployment "app" successfully rolled out`; replica counts match the request exactly: `replicas=2 updated=2 ready=2 available=2 unavailable=none`.
- **Pods stable**: both pods `1/1 Running`, `restarts=0`, container `ready=true`, `state=running`, and **empty `lastState`** (no OOM restart since the patch), observed continuously for 3m8s.
- **Original symptom gone**: no `OOMKilled`, `BackOff`, or `Unhealthy` events for the new pods — only the normal `Scheduled` event. The only remaining warnings in the namespace are historical, timestamped before the patch.
- **Actual serving confirmed** (not just object health): `HTTP 200` from inside each pod on `127.0.0.1:80` and across the pod network (`10.244.0.9 -> 10.244.0.10:80`), returning the nginx welcome page.
- **Intended image running**: `image=nginx:1.31.5`, `limits={"memory":"128Mi"}`, readiness probe still `tcp-socket :http`, service port still 80.
